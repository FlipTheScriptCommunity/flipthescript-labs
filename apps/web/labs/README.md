# Labs

Interactive labs that mock the real AWS Console, embedded in course pages at
`/courses/<courseId>/labs/<labId>`. Each lab is a small standalone React +
[Cloudscape](https://cloudscape.design) app that runs entirely in the
browser — no AWS account, no backend, no cost.

This file is the playbook for adding a new lab. Follow it (and copy from the
existing labs) so every lab looks and behaves the same.

## Current labs

All six live in the `aws-foundations` course.

| Lab    | Source                 | Built output                  | Flow                                                                   |
| ------ | ---------------------- | ----------------------------- | ---------------------------------------------------------------------- |
| EC2    | `apps/web/labs/ec2`    | `apps/web/public/labs/ec2`    | Launch an instance → success view                                      |
| S3     | `apps/web/labs/s3`     | `apps/web/public/labs/s3`     | Create bucket → objects list → upload a file → upload success          |
| VPC    | `apps/web/labs/vpc`    | `apps/web/public/labs/vpc`    | Create VPC ("VPC and more") with a live resource map → result view     |
| IAM    | `apps/web/labs/iam`    | `apps/web/public/labs/iam`    | Create user wizard (3 steps) → user page with a policy simulator       |
| RDS    | `apps/web/labs/rds`    | `apps/web/public/labs/rds`    | Create database (Standard create) with a cost estimate → database page |
| Lambda | `apps/web/labs/lambda` | `apps/web/public/labs/lambda` | Create function → function page: edit, deploy and really run the code  |

Pick the closest one as your starting point: **EC2**, **VPC** or **RDS**
for a single long form with a summary panel, **IAM** for a multi-step
wizard, **S3** or **Lambda** for a flow with several screens.

## How a lab is wired

1. **Source** lives in `apps/web/labs/<labId>/`. It has its own
   `package.json` and is _not_ a Bun workspace member (the root workspaces are
   `packages/*`, `apps/*`, `libs/*` and `infra/*`), so the root `bun install`
   never installs its dependencies and the Next.js app never imports it.
2. **`build.js`** bundles `client/index.jsx` with Bun's native bundler and
   writes `bundle.js` + `bundle.css` into `apps/web/public/labs/<labId>/`.
3. **`apps/web/public/labs/<labId>/index.html`** is a small, hand-written,
   committed shell that loads those two files.
4. **`apps/web/src/data/courses.ts`** registers the lab in a course, with
   `embedPath: '/labs/<labId>/index.html'`.
5. The generic lab route (`src/app/courses/[courseId]/labs/[labId]/page.tsx`)
   renders `LabEmbed` (`src/components/labs/lab-embed.tsx`), which loads the
   shell in a sandboxed `<iframe>` with a fullscreen toggle. No route code is
   needed per lab.

**Why an iframe:** the site is RTL Hebrew with a dark theme, while a lab must
look like the real console (light theme, LTR, Cloudscape's own global styles).
The iframe keeps the two design systems from leaking into each other.

**CI never builds labs.** The bundles are committed. After any change to a
lab's source you must rebuild it and commit the new bundles yourself.

## Directory layout

```text
apps/web/labs/<labId>/
  README.md             # what this lab covers (see "Lab README" below)
  package.json          # "@flipthescript-academy/lab-<labId>", devDependencies only
  bun.lock              # commit it, so `bun install` is reproducible
  build.js              # Bun.build → ../../public/labs/<labId>
  eslint.config.mjs     # makes the lab its own Nx project with a `lint` target
  client/
    index.jsx           # mounts <App />, imports Cloudscape global styles + styles.css
    App.jsx             # console shell, all state, screen switching, tutorial on/off
    data.js             # static reference data (regions, types, options…)
    mock<Action>.js     # fake API call(s): validation + delay + fake ids
    sections/*.jsx      # one Cloudscape <Container> per form section / screen
    TutorialOverlay.jsx # guided walkthrough UI
    tutorialSteps.js    # walkthrough copy, Hebrew + English
    styles.css          # shared base + lab-specific classes

apps/web/public/labs/<labId>/
  index.html            # hand-written shell (committed)
  bundle.js             # generated by build.js, never edit by hand
  bundle.css            # generated by build.js, never edit by hand
```

## Conventions every lab follows

### The console shell (`App.jsx`)

- Same `TopNavigation` as the other labs: the `AWS` identity, the
  `N. Virginia` region button, a **Help** button (`variant: 'primary-button'`)
  that calls `openTutorial`, the notification and settings icons, and the
  `student@flipthescript.dev` menu. Copy it as is.
- Wrap it in `<div id="top-nav">` and pass `headerSelector="#top-nav"` to
  `AppLayout`.
- `SideNavigation` and `BreadcrumbGroup` use the real console's labels for
  that service. Links are `#` placeholders.
- `toolsHide={true}`.
- The form page is a `ContentLayout` with an `h1` `Header` that uses the real
  console's page title and description, plus a **Cancel** action.
- Two-column `launch-grid` layout: the sections on the left, a sticky summary
  panel on the right (`id="section-summary"`) holding the primary action
  button (e.g. Launch instance, Create bucket, Create VPC).
- Match the real console's layout when it differs. IAM's real "Create
  user" flow is a three-step wizard, so the IAM lab uses Cloudscape's
  `Wizard`. Lambda's real "Create function" page has no summary panel, so
  it ends with Cancel / Create function buttons instead. Explain any such
  difference in the lab's own README.
- Copy `scrollEmbedIntoView()` from an existing `App.jsx` unchanged. It
  scrolls the iframe into view below the site's sticky header when the
  tutorial opens.
- The lab UI stays in **English**, with the real console's exact wording, so
  students learn what they will actually see in AWS.

### Sections

- One file per form section in `client/sections/`, each rendering a
  Cloudscape `Container` and taking `{ state, setState }` props (state lives
  in `App.jsx`).
- In `App.jsx`, wrap each one in `<div id="section-<name>">`. Those ids are
  what the tutorial spotlights.

### Mock backend (`mock<Action>.js`)

- No network calls. Validate the input with the **real** AWS rules (e.g. S3
  bucket naming rules, VPC CIDR between /16 and /28) and throw an `Error`
  with a console-like message when it's invalid. `App.jsx` shows the message
  in the summary panel.
- Wait for a short fake delay (a few hundred ms), then return realistic fake
  ids with the real prefixes (`i-`, `vpc-`, `subnet-`, `igw-`, …).

### Guided tutorial

- Opens automatically on load (`tutorialActive` starts as `true`). The Help
  button reopens it.
- `tutorialSteps.js` exports `TUTORIAL_CONTENT` with `he` (default) and `en`
  versions. Each step's `targetId` must match a `section-*` id in `App.jsx`.
- In Hebrew text, wrap every English term, field name, or number with the
  `en()` helper. `TutorialOverlay`'s `renderBidi()` turns those into
  `<bdi dir="ltr">` so they don't scramble inside RTL sentences.
- Multi-screen labs key the content by screen and pass a `section` prop to
  `TutorialOverlay` (see the S3 lab, which has a `create` and an `upload`
  walkthrough). Each screen's walkthrough opens the first time that screen
  is shown.
- In the IAM and Lambda labs, a screen whose content has no `welcome` skips
  the welcome popup and goes straight to the spotlight steps — use that for
  screens in the middle of a flow (like IAM's wizard steps 2 and 3).
- Every `targetId` must exist on the screen when its step shows. Don't
  target something that only renders conditionally; wrap it in a `div` with
  the id that's always there.

### Styles (`styles.css`)

- Copy the shared base from an existing lab: page background, sticky
  `#top-nav`, the `launch-grid` / summary layout, the tutorial classes, and
  the FlipTheScript-branded `fts-*` classes (gold / blue / purple buttons and
  the language toggle).
- Prefix lab-specific classes with the lab id (e.g. `.ami-tile-*` in EC2,
  `.vpc-map-*` in VPC).
- Don't change a shared rule in only one lab. The shared code (base styles,
  `TutorialOverlay`, `scrollEmbedIntoView`) is copied into each lab on
  purpose so every lab stays self-contained. If you fix a bug in it, fix it in
  every lab.

### `index.html`

Copy an existing one and change the `<title>` and the two `/labs/<labId>/`
paths. Keep `dir="ltr"` on `<div id="app">`; the comment in the file explains
why it must stay.

### Lab README

Every lab has its own `README.md` with the same sections as the existing
ones: a one-line intro, **Why isolated / embedded via iframe** (can point to
the EC2 README), **Rebuilding**, **What's simulated vs. real**, and the
**Flow**.

## Adding a new lab — checklist

1. Create a branch off `main`.
2. Copy the closest existing lab into `apps/web/labs/<labId>/` (skip its
   `node_modules`).
3. Update `package.json` (`name`, `description`), the output path in
   `build.js`, and the comment in `eslint.config.mjs`.
4. Write `data.js`, the mock(s), the sections, `App.jsx`, and
   `tutorialSteps.js`.
5. Create `apps/web/public/labs/<labId>/index.html`.
6. Build:

   ```sh
   cd apps/web/labs/<labId>
   bun install
   bun run build
   ```

7. Register the lab in `apps/web/src/data/courses.ts`:
   - `id`: the `<labId>` (used in the URL)
   - `title`: the service name (e.g. `'RDS'`)
   - `summary`: one Hebrew sentence
   - `embedPath`: `'/labs/<labId>/index.html'`
   - `about`: two Hebrew paragraphs. The first explains what the service is.
     The second explains what the lab practices, and says it's a free mock
     environment not connected to a real AWS account.

   Leaving out `embedPath` shows a "בקרוב" (coming soon) placeholder, which is
   handy for announcing a lab before it's built.

8. Write the lab's `README.md`.
9. Test it locally with `bunx nx dev web` at
   `http://localhost:3000/courses/<courseId>/labs/<labId>`:
   - The tutorial opens on load. Every step spotlights the right section, in
     both Hebrew and English.
   - The Help button reopens the tutorial.
   - The main action succeeds and shows the result screen.
   - Invalid input shows a validation error.
   - The browser console shows no errors from the lab.
10. Format and lint before pushing. CI runs the same checks, and a missed
    format step is what failed the first S3/VPC PR:

    ```sh
    bunx nx format:write
    bunx nx format:check --base=origin/main
    bunx nx run-many -t lint
    ```

11. Commit the source (including `bun.lock`), `public/labs/<labId>/` (the
    shell and both bundles), and `courses.ts`, then open a PR.

## Gotchas

- `bundle.js` / `bundle.css` are excluded in `.prettierignore` and in the web
  app's ESLint config. `index.html` is **not**, so Prettier checks it.
- The web app's ESLint config ignores `labs/**`. A lab is only linted if it
  has its own `eslint.config.mjs`.
- Forgetting to rebuild after a source change won't fail CI. The site keeps
  serving the old bundle.
- The bundles are big (about 1 MB JS and 2 MB CSS) because of Cloudscape.
  That's expected.
- The lab lint config flags empty functions. For a control that's shown
  only so the page matches the real console (e.g. a select with a single
  option), pass a named no-op like `const keepOnlyOption = () => undefined;`
  with a comment, not `() => {}`.
- Code that runs in a Web Worker (the Lambda lab's `runtime.js`) must use
  `globalThis`, not `self` — lint rejects `self`.
